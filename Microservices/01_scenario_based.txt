1. Each service owns its database. How do you implement cross-service queries?
Image : 1.png
    A user wants to view their e-commerce order history, including product details and payment status.

    Data needed:

        Order details → Order Service: userId, orderId, productId
        Product details → Product Service: productId, product name, price
        User info → User Service: userId, name
        Payment status → Payment Service: orderId, payment status

    Cross-service query need:
    To show order history with product name, user details, and payment status, we need data from multiple services.

    Since each service has its own database, we cannot do a direct SQL join.

    Instead, we can:

        Query Order Service for all orders by userId.
        For each order, call Product Service to get product details.
        Call Payment Service to get payment status.
        Optionally call User Service to get user information.
        An Aggregator/Order History Service combines these responses and returns the final result to the client.

    In a microservices architecture, each service owns its own database, so we cannot directly perform SQL joins across services. 
    For example, in an e-commerce application, the Order Service has order details, the Product Service has product details, 
    and the Payment Service has payment status. If we use CQRS, we create a separate read model for queries such as “My Orders.” 
    Services publish events like `OrderCreated` and `PaymentCompleted`, and a Read Model Service consumes these events and stores 
    the required data in a denormalized database. Now, when the user requests their order history, we can query this read
     model directly instead of calling multiple services, which makes the query faster and reduces network calls.

2. How do you handle eventual consistency in user-facing flows?
    Eventual consistency is a consistency model used in distributed systems where updates to data will propagate to all nodes/services, 
    but not instantly. Over time, all nodes will have the same data, but temporary inconsistencies are allowed.

    How it works:
        When data is updated in one service/database, other services may not see the change immediately.
        The system guarantees that, given enough time and no new updates, all services will eventually reflect the latest data.

    Scenario:
    A user adds products to the cart, goes to checkout, makes the payment, and then the order is confirmed.

    How it works:
        Cart Service stores the products when the user adds items to the cart.
        User proceeds to Checkout and selects the address and payment method.
        When the user clicks “Place Order”, the Order Service creates the order with status PENDING.
        Order Service publishes an OrderCreated event.
        Inventory Service receives the event and reserves the required products.
        Payment Service processes the payment.
        When payment succeeds, Payment Service publishes PaymentCompleted.
        When inventory is successfully reserved, Inventory Service publishes InventoryReserved.
        Order Service receives both events. If payment and inventory are successful, it changes the order status from PENDING → CONFIRMED.
        Order Service publishes OrderConfirmed.
        Notification Service consumes this event and sends an order-confirmation email/notification to the user.


        Where eventual consistency happens

        Immediately after the user clicks Place Order, we may have:
        Order Service       → PENDING
        Payment Service     → PROCESSING
        Inventory Service   → RESERVING
        Notification        → Not sent yet

        A few seconds later:
        Payment Service     → PAID
        Inventory Service   → RESERVED
        Order Service       → CONFIRMED
        Notification        → "Your order is confirmed"

    How to handle:

    1. UI/UX Patterns for Temporary Inconsistencies:
     - When the user places an order, immediately show “Order processing…” instead of waiting for payment and inventory services to finish.
     - Display the current order status as PENDING and a message such as “Your order is being confirmed. This may take a few moments.”
     - Provide a Refresh/View Order Status option so the user can check the latest status.
     - Once payment and inventory are successfully processed and the order becomes CONFIRMED, show the confirmation to the user.
     - If the order fails, clearly show “Order failed” and provide an option to retry.
     - Send an email/in-app notification when the order is finally confirmed or failed.

    2. Backend Patterns:
     - Make order and payment operations idempotent. If the user clicks Place Order again because of a network issue or timeout, 
       the system should not create a duplicate order or charge the customer twice.
     - Order Service subscribes to events from Payment and Inventory services, such as PaymentCompleted, PaymentFailed, 
       and InventoryReserved, instead of continuously polling those services.
     - Update the Order Service database as events arrive. For example, when PaymentCompleted and InventoryReserved are received, 
       Order Service updates the order from PENDING → CONFIRMED.
     - The client can query the Order Service to get the latest order status, while Notification Service can notify the user 
       when the order is confirmed or failed.

3. A transaction spans multiple services. How do you ensure consistency without 2PC?
    2PC is a distributed transaction protocol used to ensure all-or-nothing outcomes across multiple services or databases.
    It coordinates a transaction across several participants (e.g., services or databases) so that either all commit or all abort, 
    maintaining consistency.

    Phases:
    1. Prepare Phase (Voting):
        The coordinator asks all participants if they can commit.
        Each participant does necessary checks and replies:
        "Yes" (ready to commit)
        "No" (cannot commit)

    2. Commit Phase:
        If all participants replied "Yes", the coordinator tells everyone to commit.
        If any participant replied "No", the coordinator tells everyone to abort/rollback.

    In a booking system:
        2-Phase Commit (2PC) – E-commerce Example
        Scenario: A user buys an iPhone for ₹50,000.
        1. Order Service acts as the coordinator
            Creates the order with status PENDING.
            Starts a distributed transaction with Inventory Service and Payment Service.
        2. Prepare Phase
            Inventory Service: Checks whether the iPhone is available and temporarily reserves the product. It responds PREPARED.
            Payment Service: Checks whether the customer's card has sufficient balance/credit and temporarily reserves/authorizes ₹50,000. It responds PREPARED.
            At this point, nothing is permanently committed.
        3. Commit Phase
            If both services respond PREPARED, Order Service sends COMMIT.
            Inventory Service: Permanently reserves the iPhone.
            Payment Service: Permanently captures the ₹50,000.
            Order Service: Changes order status from PENDING → CONFIRMED.
        4. If any service fails
            Suppose Inventory responds PREPARED, but Payment cannot authorize the amount.
            Order Service sends ABORT.
            Inventory releases its temporary reservation.
            Payment does not capture any money.
            Order Service marks the order as FAILED.

    - In 2PC, if all participants say "yes" in the prepare phase but a commit fails in one service during the commit phase, 
        the system enters an inconsistent state. This is a known limitation of 2PC:
    - The coordinator tells all participants to commit.
    - If one participant fails to commit (e.g., due to a crash or network issue), but others have already committed, some services have
         the transaction while others do not.
    - Recovery is complex: the failed participant must recover and try to complete the commit when it comes back online, but if it cannot, 
        manual intervention may be needed.

    How do you ensure consistency in a microservices architecture?
        Use eventual consistency with an event-driven architecture. For example, in an e-commerce application:

        * Order Service creates an order with status PENDING when the user clicks Place Order.
        * Order Service publishes an OrderCreated event to Kafka.
        * Inventory Service consumes the event and reserves the product. It publishes InventoryReserved or InventoryFailed.
        * Payment Service processes the payment. It publishes PaymentCompleted or PaymentFailed.
        * Order Service listens to these events:
            - If payment and inventory both succeed → order becomes CONFIRMED.
            - If either fails → order becomes FAILED.
        * If one operation succeeds and another fails, use compensating actions:
            - Payment succeeded but inventory failed → refund the payment.
            - Inventory was reserved but payment failed → release the inventory.
        * Make operations idempotent so retries or duplicate events do not create duplicate orders, payments, or reservations.
        * The client can query the Order Service to get the latest order status.

4. How do you design idempotent APIs in distributed systems?

    Assign a unique idempotency key to each client request (e.g., UUID, client-generated token).
    API receives the request with the idempotency key in a header or body.
    On first request:
        Process the operation.
        Store the idempotency key and response/result in a persistent store (e.g., database, cache).
        On repeated requests with the same idempotency key:
            Detect the key in the store.
            Return the previously stored response/result without re-processing.
            Ensure all side effects (DB writes, events) are only performed once per idempotency key.

    Example: E-commerce order placement

    The client sends a Place Order request with an idempotency key, for example:
    Idempotency-Key: K12345
     * The Order Service receives the request and generates the actual orderId itself, for example O1001. The client does not generate the order ID.
     * Order Service stores the idempotency key and order information together, with a unique constraint such as (userId, idempotencyKey), 
       so concurrent retries cannot create two orders.
     * The Order Service creates:
       Order O1001 → PENDING

    and publishes:

    OrderCreated(O1001)
     * Suppose the client does not receive the response because of a network timeout and sends the same request again with K12345.
     * Order Service finds that K12345 has already been processed and returns the existing O1001 instead of creating another order.
     * The same principle must be applied to downstream services.

    Payment Service:

    Receives OrderCreated(O1001).
     * Processes the payment and stores that O1001 has been processed.
     * If the same event is received again, it detects O1001 is already processed and does not charge the customer again.

    Inventory Service:

    Receives OrderCreated(O1001).
    * Reserves the product and stores the reservation against O1001.
    * If the same event is received again, it detects that the reservation already exists and does not reserve the product again.

    So the flow is:
        
        Client
        |
        | Idempotency-Key = K12345
        ↓
        Order Service
        |
        | generates orderId = O1001
        ↓
        Order = PENDING
        |
        | OrderCreated(O1001)
        ↓
        ┌───────────────┬────────────────┐
        ↓               ↓
        Payment        Inventory
        Service        Service
        ↓               ↓
        O1001           O1001
        already         already
        processed       reserved
        ↓               ↓
        No duplicate    No duplicate
        charge          reservation

    Key point: The client may provide the idempotency key to identify a retry, but idempotency is enforced by the server and database. 
    Each service independently ensures that the same business operation, such as an order, payment, or inventory reservation, 
    is processed only once.

5. How do you deal with duplicate requests caused by retries?
    I would use idempotency at each service so that a retry does not repeat the same side effect.

    Example: E-commerce order

        * Client sends a Place Order request with an idempotency key.
        * Order Service generates the orderId, for example O1001, and stores the key with that order.
        * If the client retries because of a timeout, Order Service detects that the request was already processed and returns O1001 
          instead of creating another order.
        * Order Service publishes OrderCreated(O1001) to Kafka.
        * Payment Service uses O1001 as the idempotency reference. If the same event is received again, 
          it detects that payment for O1001 was already processed and does not charge the customer again.
        * Inventory Service similarly checks whether inventory for O1001 has already been reserved and avoids reserving it again.
        * Use database unique constraints/transactions to make these checks safe even when two identical requests arrive at the same time.

    So:

        Retry
        ↓
        Order Service → same orderId O1001
        ↓
        Payment       → no duplicate charge
        Inventory     → no duplicate reservation

    Key idea: retries are expected in distributed systems, so every operation with side effects should be designed to be idempotent.

*************** Reliability & resilience *****************

1. One service failure brings down multiple services. What design mistake was made?

    - In a booking system, services like Booking, Inventory, Payment, and User should be loosely coupled.
    - If one service failure (e.g., Payment Service is down) causes all other services (Booking, Inventory, User) to fail or 
       become unavailable, the design mistake is tight coupling and lack of fault isolation.
    - Common mistakes:
        Synchronous/blocking calls between services (e.g., Booking waits for Payment to respond before replying to client).
        No timeouts, retries, or circuit breakers.
        No fallback or compensation logic.
        Direct database access across services.
        No asynchronous/event-driven communication.

Note : In a booking system, if Booking Service synchronously calls Inventory and Payment Services and waits for their responses, 
any failure or slowness in those services will block the Booking Service. This can lead to cascading failures: one service outage
 propagates and brings down the entire system.

    Correct design:
        1. Use asynchronous communication (e.g., events, messaging) so Booking Service does not block waiting for other services.
        2. Implement timeouts and circuit breakers for remote calls.
        3. Design for graceful degradation: if Payment Service is down, Booking can mark the booking as "PENDING" and notify the user, 
          rather than failing completely.
        4. Avoid direct database access between services.
        5. Use compensation logic to handle failures (e.g., release reserved inventory if payment fails).

2. How do you design timeouts, retries, and circuit breakers correctly?

    1. Timeout:
        Set a maximum duration for the Booking Service’s HTTP/gRPC call to Inventory Service.
        If Inventory does not respond within the timeout, abort the call and handle as a failure.

    2. Retry:
        On timeout or transient error, retry the call a limited number of times.
        Use exponential backoff between retries to avoid overwhelming Inventory Service.

    3. Circuit Breaker:
        Track the success/failure rate of calls to Inventory Service.
        If failures exceed a threshold, open the circuit and block further calls for a period.
        After cooldown, allow a few test calls (half-open); if successful, close the circuit.

3. What is the risk of aggressive retries and how do you mitigate it?
    When Booking service calls Inventory service (to lock/hold a seat/room), aggressive retries are dangerous because they multiply load 
    exactly when Inventory is already unhealthy, and they can also create incorrect inventory state.
    
    Risks (Booking → Inventory)
    1) Retry storm → Inventory collapse
        If Inventory is slow/down:
        Booking requests time out
        Booking retries immediately (and often multiple times)
        Now Inventory gets N× traffic while it’s already struggling
        Result: Inventory stays down longer, and Booking starts failing too (cascading failure).

        Example: 5,000 bookings/min × 3 retries = 15,000 extra lock attempts/min.

    2) Thundering herd
        If many bookings fail at the same time, and all retry with the same schedule (e.g., every 1s),
        they “sync up” and hit Inventory in waves, causing repeated spikes and continued timeouts.

    3) Duplicate locks / inconsistent inventory (double hold)
        Inventory “lock/hold” is a state-changing operation.
        If Booking retries after a timeout, the first request may have actually succeeded but the response was lost.
        So Booking sends another lock:
            Inventory may create multiple holds for the same booking attempt
            Inventory gets artificially reduced
            You get “sold out” incorrectly, or holds leak until expiry
            This is a correctness bug, not just performance.

    4) Holding threads and resources in Booking
        Each retry keeps Booking threads busy waiting on Inventory.
        Thread pools saturate → Booking becomes slow/unavailable even for requests that don’t need Inventory yet.

4. How do you design graceful degradation in microservices?
    1. Identify critical flows in the e-commerce system: order creation, inventory reservation, payment.
    2. For each dependency, implement fallback logic in Order Service.
    3. Use timeouts, retries, and circuit breakers to detect failures quickly.
    4. If a dependency fails, Order Service should:
        Mark the order as "PENDING" or "PAYMENT_PENDING" instead of failing.
        Inform the user that order confirmation or payment is delayed.
        Allow the user to check the order status later.
        Log the degraded operation for monitoring and alerting.

    Example: Amazon/Flipkart-like e-commerce app

    * If Inventory Service is unavailable, Order Service creates the order with status "PENDING" and informs the user 
      that product availability will be confirmed later.
    * If Payment Service is unavailable, Order Service marks payment as "PENDING" and informs the user that payment confirmation will follow.
    * Order Service uses circuit breakers and fallback logic to handle these failures.
    * UI displays intermediate states like "Processing" or "Payment Pending" and allows the user to check the status later.

5. What does a good health check look like in microservices?

    A good health check in microservices should quickly tell us whether a service is able to do its job.

    For example, in an e-commerce application:

    * Liveness check – checks whether the service is running.
        Example: Order Service is alive and responding.
    * Readiness check – checks whether the service is ready to receive traffic.
        Example: Order Service is running, its database connection is available, and it can process orders.
    * Dependency checks – check important dependencies like database, cache, or message broker.
        But don't make the health check too heavy or call every downstream service unnecessarily.
    * Fast and lightweight – health checks should return quickly and should not perform real business operations.

    Example:

    /health/live → 200 OK → service is running.
    /health/ready → 200 OK → service is ready to accept requests.
    If the database is unavailable, readiness can return 503, so Kubernetes/load balancer can stop sending traffic to that instance.

Observability & debugging
1. A request flows through multiple services and fails intermittently. How do you debug it?
    First, I trace a single failing request using trace/correlation ID to find which service or dependency is failing. 
    Then I check metrics like p99 latency, error rate, and resource saturation to see patterns like peak-load issues or 
    instance-specific failures. I classify whether it’s timeout, retry storm, or resource exhaustion. Finally, I stabilize
    quickly using tighter timeouts, limited retries with backoff, and circuit breakers while investigating root cause.

3. Logs show success but users see failures. What could be wrong?
    Where this could occur in a booking system:

    Booking Creation:
    If the Booking Service logs "Booking created successfully" after writing a record to the database, but before confirming payment or 
    inventory reservation, the log shows success. If payment or inventory fails later, the user sees a failed booking.

    Asynchronous Processing:
    If the Booking Service logs success after publishing an event (e.g., to reserve inventory or process payment), but the downstream 
    service fails to process the event, the log shows success but the user sees failure.

    Partial Failure:
    If the Booking Service logs success after one step (e.g., payment processed), but inventory reservation fails, the log shows success 
    for payment, but the overall booking fails for the user.

    Error Handling:
    If exceptions are caught and not logged after a success log, or if the log is written before all steps complete, logs may show success 
    while the user sees an error.

    User Notification:
    If the system logs that a notification/email was sent, but the email service fails after logging, the user does not receive confirmation.

5. How do you monitor SLA(Service Level Aggrement)/SLOs(Service Level Objective) across multiple services?
    1. Define SLOs/SLAs for each booking system service (e.g., Booking, Inventory, Payment):
        Example: 99.9% availability, 95% of requests < 200ms, <1% error rate.
    2. Instrument each service to expose metrics (latency, error rate, availability) using Spring Boot Actuator.
    3. Use Prometheus to scrape metrics from all services.
    4. Use Grafana to visualize metrics and create SLO/SLA dashboards.
    5. Set up Prometheus alert rules for SLO/SLA breaches.
    6. Aggregate metrics for end-to-end booking flow monitoring.

2. How do you secure service-to-service communication?
    Use HTTPS (TLS) for all service-to-service communication.
    Implement authentication between services, commonly with mutual TLS (mTLS) or tokens (JWT/OAuth2).
    Authorize requests using scopes/roles.
    Rotate and manage secrets/keys securely.
    Optionally, use a service mesh (e.g., Istio) for automated mTLS and policy enforcement.

    1. Use HTTPS (TLS) for all service-to-service communication
        • All internal REST/gRPC calls between microservices (e.g., Booking Service and Payment Service) use HTTPS endpoints.
        • Example:
        Booking Service calls https://payment-service.internal/pay instead of http://payment-service.internal/pay.
        • TLS encrypts data in transit, preventing eavesdropping.

    2. Implement authentication between services (mTLS or JWT/OAuth2)
        • Each service must prove its identity to others.
        • Example with JWT/OAuth2:
        Booking Service obtains a JWT token from an Auth Service, attaches it as
        Authorization: Bearer <token> when calling Payment Service.

        • Example with mTLS:
        Both Booking and Payment services have client/server certificates. When Booking Service connects, both sides verify each other’s certificates.

    3. Authorize requests using scopes/roles
        • Services only allow actions if the caller has the right permissions.
        • Example:
        Payment Service checks the JWT token’s scopes/roles. Only services with ROLE_BOOKING can initiate payments; only ROLE_ADMIN can issue refunds.

    4. Rotate and manage secrets/keys securely
        • Store secrets (JWT signing keys, TLS certs) in a secure vault (e.g., HashiCorp Vault, Azure Key Vault).
        • Example:
        Regularly rotate the TLS certificates used by Booking and Payment services. Update JWT signing keys and distribute them securely.

    5. Use a service mesh (e.g., Istio) for automated mTLS and policy enforcement
        • Service mesh injects sidecar proxies to handle mTLS, authentication, and authorization automatically.
        • Example:
        Istio ensures all traffic between Booking and Payment services is encrypted with mTLS, and enforces policies (e.g., only Booking Service can call Payment Service’s /pay endpoint).

4. How do you manage secrets without hard-coding them?
    In a booking system, we never hard-code secrets like database passwords, payment gateway keys, or JWT signing keys. Instead, we store them in a 
    centralized secrets manager like Vault or a cloud secret manager. Each microservice, like Booking or Payment, retrieves secrets at runtime using 
    its identity, such as a Kubernetes service account or IAM role. We also use short-lived credentials, automatic rotation, and strict access 
    policies to reduce risk.

    I don’t put secrets in code or Git. I store them in a secure place like a secrets manager or encrypted config. The application reads them 
    at runtime using environment variables or secure files. I make sure only required services can access them, and I rotate them regularly.

*********** Deployment & versioning *************
1. How do you deploy microservices with zero downtime?
    Deployment Strategy:
    Use rolling updates to replace service instances one at a time, or blue-green deployments to run old and new versions in parallel 
    and switch traffic when ready. Canary releases can route a small percentage of traffic to the new version first.

    Stateless Services:
    Design booking, payment, and inventory services so they do not store session or user data locally. Store all state in external 
    systems (databases, distributed caches) so any instance can handle any request.

    Health Checks:
    Configure readiness and liveness checks for each service. The orchestrator only sends traffic to instances that pass these checks, 
    preventing users from hitting unhealthy or starting/stopping services.

    Traffic Management:
    Use a load balancer or orchestrator to distribute requests. During deployment, new instances are started and added to the load balancer 
    only after passing health checks. Old instances are removed only after new ones are ready.

    Overlap and Gradual Replacement:
    Ensure new and old versions run simultaneously during deployment. This overlap allows uninterrupted service as traffic shifts from old to new.

    Monitoring and Rollback:
    Continuously monitor application health and user experience during deployment. If issues are detected, automatically or manually rollback 
    to the previous version.

    Automation:
    Use CI/CD tools to automate build, test, and deployment steps. Automation reduces human error and speeds up the process, making zero-downtime 
    deployments more reliable.

    Summary:
    Zero-downtime deployment in a booking system is achieved by gradually replacing service instances, ensuring only healthy instances 
    serve traffic, externalizing state, and automating the process for reliability and speed.

2. How do you handle database schema changes in live systems?
    1. Design schema changes to be backward compatible
        Add new columns/tables, avoid removing or renaming existing fields.
        If you must remove/rename, plan a phased migration.

    2. Use a migration tool
        Use Liquibase or Flyway to version and automate schema changes.

    3. Phased deployment steps:
        Step 1: Deploy schema changes that work with both old and new service versions.
        Step 2: Deploy new Inventory Service code that uses the new schema.
        Step 3: After all consumers are updated, remove deprecated schema elements.

    4. Test migration in staging
        Apply schema changes in a test environment first.

    5. Monitor after deployment
        Check application and database logs for errors.

    6. Rollback plan
        Prepare scripts to revert schema changes if needed.
